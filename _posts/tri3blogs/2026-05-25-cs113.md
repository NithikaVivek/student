## Data Structures

### Collections

Java's Collections Framework is the backbone of my backend. Rather than using raw arrays, I leveraged `ArrayList`, `HashMap`, and `HashSet` throughout my models and controllers to handle dynamic, runtime data efficiently.

**Example — managing a list of users returned from the database:**
```java
// UserController.java
@GetMapping("/all")
public ResponseEntity<List<User>> getAllUsers() {
    List<User> users = userService.findAll(); // backed by ArrayList
    return ResponseEntity.ok(users);
}
```

Using `ArrayList` here is an O(1) amortized append and O(n) traversal — ideal for ordered iteration. When I needed O(1) average-case lookup by ID, I switched to a `HashMap`.

**Why it matters:** Choosing the right collection is the difference between O(n) and O(1) lookups. This isn't academic — at scale, that gap is the difference between a responsive app and a broken one.

### Lists

List operations — add, remove, search, and iterate — are used throughout my service layer whenever I process ordered sequences of data.

**Example — filtering active tasks from a list:**
```java
// TaskService.java
public List<Task> getActiveTasks(List<Task> allTasks) {
    List<Task> active = new ArrayList<>();
    for (Task t : allTasks) {
        if (t.isActive()) active.add(t);  // O(1) amortized
    }
    return active;
}
```

- **add**: O(1) amortized for `ArrayList`
- **remove by index**: O(n) shift cost — noted in code comments
- **search**: O(n) linear scan; O(log n) if list is sorted and binary search is applied
- **iterate**: O(n) using enhanced for-loop or iterator

### Stacks & Queues

I applied a `Deque` (double-ended queue) as both a **stack** for undo/redo functionality and a **queue** for a background task processing pipeline.

**Stack — Undo/Redo:**
```java
// EditHistoryService.java
private Deque<Action> undoStack = new ArrayDeque<>();
private Deque<Action> redoStack = new ArrayDeque<>();

public void performAction(Action action) {
    action.execute();
    undoStack.push(action);   // O(1) push
    redoStack.clear();
}

public void undo() {
    if (!undoStack.isEmpty()) {
        Action action = undoStack.pop();  // O(1) pop
        action.undo();
        redoStack.push(action);
    }
}
```

**Queue — Task Processing:**
```java
// TaskQueueService.java
private Queue<Runnable> taskQueue = new LinkedList<>();

public void enqueue(Runnable task) { taskQueue.offer(task); }  // O(1)
public void processNext() {
    Runnable task = taskQueue.poll();  // O(1)
    if (task != null) task.run();
}
```

A **stack** enforces LIFO (Last In, First Out) — perfect for undo because the most recent action is the first to reverse. A **queue** enforces FIFO (First In, First Out) — perfect for task scheduling where fairness matters.

### Trees

I integrated the **Smile** machine learning library to apply a **Decision Tree classifier** for content recommendation. Smile builds a binary decision tree internally — splitting nodes by information gain until leaves represent class labels.

**Example — training a Decision Tree model:**
```java
// RecommendationService.java
import smile.classification.DecisionTree;
import smile.data.formula.Formula;

public void trainModel(DataFrame trainingData) {
    DecisionTree model = DecisionTree.fit(Formula.lhs("label"), trainingData);
    int[] predictions = model.predict(testData);
}
```

A **Decision Tree** is a rooted, directed acyclic tree where:
- Each **internal node** is a feature test
- Each **branch** is a test outcome
- Each **leaf** is a class prediction

Time complexity of prediction: O(depth) — typically O(log n) for balanced trees.

I also use **tree structures implicitly** through Spring's `@OneToMany` JPA relationships, which map to hierarchical parent-child data in the database (e.g., a `Course` owning many `Assignments`).

### Sets

`HashSet` is used throughout my authentication and authorization layer to manage **unique** collections — user roles, permission flags, and content tags — where duplicates are meaningless and membership checks need to be fast.

**Example — role-based access control:**
```java
// User.java
@ElementCollection(fetch = FetchType.EAGER)
private Set<String> roles = new HashSet<>();

public boolean hasRole(String role) {
    return roles.contains(role);  // O(1) average-case lookup
}
```

**Set operations used:**
- `add()` — O(1) average; silently ignores duplicates
- `contains()` — O(1) average; used in every authorization check
- `removeAll()` — O(n) set difference for revoking role batches

Using a `Set` instead of a `List` for roles eliminates accidental duplicates and brings membership checks from O(n) down to O(1).

### Dictionaries / Maps

`HashMap` (and `JSONObject` for API payloads) provide O(1) average-case key-value lookup throughout the application — from configuration loading to caching frequently-accessed records.

**Example — configuration map loaded at startup:**
```java
// AppConfig.java
private Map<String, String> config = new HashMap<>();

public void loadConfig(String[] pairs) {
    for (String pair : pairs) {
        String[] kv = pair.split("=");
        config.put(kv[0].trim(), kv[1].trim());  // O(1) average
    }
}

public String get(String key) {
    return config.getOrDefault(key, "");  // O(1) average
}
```

**Why HashMap over a sorted structure?** When I don't need ordering — just fast lookup — `HashMap`'s O(1) average beats `TreeMap`'s O(log n). I use `TreeMap` only when I need keys in sorted order (e.g., displaying settings alphabetically).

### Graphs

I modeled the **user relationship network** using an adjacency list graph to power friend recommendations and community detection.

**Graph representation:**
```java
// SocialGraph.java
private Map<Long, List<Long>> adjacencyList = new HashMap<>();

public void addEdge(Long userA, Long userB) {
    adjacencyList.computeIfAbsent(userA, k -> new ArrayList<>()).add(userB);
    adjacencyList.computeIfAbsent(userB, k -> new ArrayList<>()).add(userA);
}
```

**BFS for friend recommendations (mutual connections):**
```java
public List<Long> recommendFriends(Long userId, int maxDepth) {
    Queue<Long> queue = new LinkedList<>();
    Set<Long> visited = new HashSet<>();
    List<Long> recommendations = new ArrayList<>();

    queue.offer(userId);
    visited.add(userId);
    int depth = 0;

    while (!queue.isEmpty() && depth < maxDepth) {
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            Long current = queue.poll();
            for (Long neighbor : adjacencyList.getOrDefault(current, Collections.emptyList())) {
                if (!visited.contains(neighbor)) {
                    visited.add(neighbor);
                    queue.offer(neighbor);
                    if (depth == maxDepth - 1) recommendations.add(neighbor);
                }
            }
        }
        depth++;
    }
    return recommendations;
}
```

**Time complexity:** O(V + E) where V = users, E = connections.  
**Space complexity:** O(V) for the visited set and queue.

I also implemented **connected components** (DFS-based) for community detection — identifying clusters of users who are connected to each other but isolated from the rest of the graph.

## Algorithms

### Searching

Search is implemented at multiple layers:

**1. Linear Search — O(n)** — used in small, unsorted in-memory lists:
```java
public Optional<Task> findByTitle(List<Task> tasks, String title) {
    return tasks.stream()
                .filter(t -> t.getTitle().equalsIgnoreCase(title))
                .findFirst();
}
```

**2. Binary Search — O(log n)** — applied after sorting a list by ID:
```java
public int binarySearch(List<Integer> sortedIds, int target) {
    int lo = 0, hi = sortedIds.size() - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        int cmp = Integer.compare(sortedIds.get(mid), target);
        if (cmp == 0) return mid;
        else if (cmp < 0) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}
```

**3. Database queries — O(log n) with indexing** — Spring Data JPA translates method names into SQL:
```java
// UserRepository.java
List<User> findByLastNameContainingIgnoreCase(String query);
```
With a B-tree index on `last_name`, this runs in O(log n) at the database level.

### Sorting

I implemented sorting with `Comparator` and `Comparable` for real business logic — ordering posts by date, users by name, and recommendations by relevance score.

**Comparator chaining — sort by priority, then date:**
```java
// TaskService.java
tasks.sort(Comparator.comparingInt(Task::getPriority)
                     .thenComparing(Task::getCreatedAt, Comparator.reverseOrder()));
```

**Custom Comparable — leaderboard entries ranked by score:**
```java
public class LeaderboardEntry implements Comparable<LeaderboardEntry> {
    private int score;

    @Override
    public int compareTo(LeaderboardEntry other) {
        return Integer.compare(other.score, this.score); // descending
    }
}
```

**AP Study Sessions — Classic Sorts:**
In our AP FRQ peer teaching sessions I implemented and analyzed:

| Algorithm | Best | Average | Worst | Stable? |
|-----------|------|---------|-------|---------|
| Merge Sort | O(n log n) | O(n log n) | O(n log n) | ✅ Yes |
| Selection Sort | O(n²) | O(n²) | O(n²) | ❌ No |
| Insertion Sort | O(n) | O(n²) | O(n²) | ✅ Yes |

Java's `Collections.sort()` / `Arrays.sort()` uses **TimSort** (a hybrid of Merge + Insertion) — O(n log n) worst case, O(n) best case on nearly-sorted data. This is why I trust `Comparator`-based sorting for production rather than rolling my own.

### Hashing

Hashing appears in three distinct contexts in my project:

**1. Password hashing with BCrypt:**
```java
// AuthService.java
@Autowired
private PasswordEncoder passwordEncoder; // BCryptPasswordEncoder

public User register(String username, String rawPassword) {
    String hashed = passwordEncoder.encode(rawPassword);  // bcrypt, cost factor 12
    return userRepository.save(new User(username, hashed));
}

public boolean authenticate(String raw, String hashed) {
    return passwordEncoder.matches(raw, hashed);
}
```

BCrypt is a **one-way hash function** with a configurable cost factor — making brute-force attacks computationally expensive.

**2. HashMap internals — O(1) average lookup:**  
When I call `map.get(key)`, Java computes `key.hashCode()`, mods it into a bucket index, and retrieves the value. Collisions are handled via chaining. Average case O(1); worst case O(n) with degenerate hashing.

**3. Data integrity — checksums:**
```java
MessageDigest md = MessageDigest.getInstance("SHA-256");
byte[] hash = md.digest(fileBytes);
String checksum = HexFormat.of().formatHex(hash);
```

### Algorithm Analysis

Every non-trivial algorithm in my codebase is annotated with Big-O analysis:

```java
/**
 * Finds mutual connections between two users using BFS.
 *
 * Time Complexity:  O(V + E) — visits each vertex and edge once
 * Space Complexity: O(V) — visited set and queue at most hold all vertices
 *
 * @param userA first user ID
 * @param userB second user ID
 * @return list of shared connection IDs
 */
public List<Long> getMutualConnections(Long userA, Long userB) { ... }
```

**Key complexity decisions I made:**
- Chose `HashSet` over `List` for membership checks: O(1) vs O(n)
- Chose `HashMap` over `TreeMap` for config lookups: O(1) vs O(log n)
- Added a DB index on `user_id` in the posts table: query from O(n) to O(log n)
- Cached the leaderboard result in memory: O(1) retrieval after initial O(n log n) sort

## Object-Oriented Design

### Abstraction

Abstract classes and interfaces define the **contracts** that my application components implement — separating *what* a component does from *how* it does it.

**Interface contract for all notification types:**
```java
// Notifiable.java
public interface Notifiable {
    void send(String recipient, String message);
    boolean isDelivered();
}

// EmailNotification.java
public class EmailNotification implements Notifiable {
    @Override
    public void send(String recipient, String message) { /* SMTP logic */ }

    @Override
    public boolean isDelivered() { /* check delivery status */ }
}
```

**Abstract base class for shared repository logic:**
```java
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private LocalDateTime createdAt = LocalDateTime.now();

    public abstract String getSummary(); // subclasses must implement
}
```

---

### Encapsulation

All domain model fields are `private`. External code interacts only through public getters/setters, keeping internal representation hidden.

```java
// Post.java
public class Post extends BaseEntity {
    private String title;
    private String content;
    private boolean published;

    public String getTitle() { return title; }
    public void setTitle(String title) {
        if (title == null || title.isBlank()) throw new IllegalArgumentException("Title required");
        this.title = title;
    }

    public boolean isPublished() { return published; }
    // No direct field access — invariants enforced in setters
}
```

Encapsulation prevents invalid state (e.g., blank titles) and lets me change the internal representation later without breaking callers.

---

### Inheritance

I use class hierarchies to share behavior while allowing specialization:

```java
// User.java (base class)
public class User extends BaseEntity {
    private String username;
    private String email;
    private String passwordHash;

    public String getDisplayName() { return username; }
}

// Student.java
public class Student extends User {
    private String gradeLevel;
    private List<Course> enrolledCourses = new ArrayList<>();

    @Override
    public String getDisplayName() {
        return "[Student] " + super.getDisplayName();
    }
}

// Teacher.java
public class Teacher extends User {
    private String department;
    private List<Course> taughtCourses = new ArrayList<>();
}
```

`Student` and `Teacher` inherit all `User` fields and methods but override or extend behavior where needed.

### Polymorphism

Method overriding and interface polymorphism let my code treat different types uniformly:

```java
// Polymorphic method — works for any Notifiable
public void notifyUser(Notifiable notifier, String user, String msg) {
    notifier.send(user, msg);  // dispatches to Email, SMS, or Push at runtime
}

// Called with different concrete types:
notifyUser(new EmailNotification(), "alice@example.com", "Welcome!");
notifyUser(new SMSNotification(), "+17025551234", "Code: 8472");
```

**Runtime polymorphism** (dynamic dispatch) means I can add a new `SlackNotification` without changing `notifyUser` at all — open/closed principle in action.

### Design Patterns

**1. MVC (Model-View-Controller)** — Spring Boot enforces this naturally:
- **Model**: JPA entity classes (`User`, `Post`, `Task`)
- **Controller**: `@RestController` classes handling HTTP routing
- **View**: JSON responses consumed by the frontend

**2. Repository Pattern** — data access is abstracted behind interfaces:
```java
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
}
// Service layer calls repository; never writes SQL directly
```

**3. Singleton Pattern** — Spring manages all `@Service` and `@Repository` beans as singletons by default. The application context holds exactly one instance of each bean, shared across all components.

**4. Factory Pattern** — used to create `ResponseEntity` objects with consistent structure:
```java
public class ResponseFactory {
    public static <T> ResponseEntity<T> ok(T body) {
        return ResponseEntity.status(HttpStatus.OK).body(body);
    }
    public static ResponseEntity<String> notFound(String msg) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(msg);
    }
}
```

### API Development

I designed a RESTful API following HTTP semantics strictly:

| Method | Endpoint | Description | Status Codes |
|--------|----------|-------------|--------------|
| `GET` | `/api/users` | List all users | 200 |
| `GET` | `/api/users/{id}` | Get user by ID | 200, 404 |
| `POST` | `/api/users` | Create new user | 201, 400, 409 |
| `PUT` | `/api/users/{id}` | Full update | 200, 404 |
| `PATCH` | `/api/users/{id}` | Partial update | 200, 404 |
| `DELETE` | `/api/users/{id}` | Delete user | 204, 404 |

**Example controller with proper `ResponseEntity` usage:**
```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public ResponseEntity<User> getUser(@PathVariable Long id) {
        return userService.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<User> createUser(@Valid @RequestBody UserDTO dto) {
        User created = userService.create(dto);
        URI location = URI.create("/api/users/" + created.getId());
        return ResponseEntity.created(location).body(created);
    }
}
```

### Ethical Considerations

**Security:** All passwords are BCrypt-hashed; no plaintext credentials anywhere in the codebase or logs. JWT tokens expire after 24 hours. HTTPS enforced via nginx redirect.

**Privacy:** Users control their own data. A `/api/users/{id}` `DELETE` endpoint hard-deletes all associated records via `CascadeType.ALL`. No third-party analytics that track users without consent.

**Accessibility:** Frontend components use semantic HTML, ARIA labels, and keyboard-navigable UI. Color contrast meets WCAG AA.

**Equity:** The platform is free and web-accessible without requiring native app installs — lowering the barrier for users on low-end devices or limited data plans.

**AI/ML Ethics:** The Decision Tree recommendation model is trained on opt-in behavioral data only. Users can view and delete their data history at any time.
